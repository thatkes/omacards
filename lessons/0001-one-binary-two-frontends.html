One binary, two frontends

Before you can change omacards safely, you need its boot map. Every other design decision hangs off one seam: the app is a GUI and a headless CLI in the same executable.

The fork in the road

Open src/main.cpp:27. The very first thing main() does is turn argv into a QStringList, then ask Cli::needsOffscreen(arguments) — before any QApplication exists (main.cpp:27–38).

if (Cli::needsOffscreen(arguments))
    qputenv("QT_QPA_PLATFORM", "offscreen");

QApplication app(argc, argv);
if (Cli::needsOffscreen(arguments))
    return Cli::run(arguments);

"Offscreen" is a Qt platform plugin: Qt still builds its object model, but paints to nothing. No window, no display server needed.

If the arguments look like an agent command, the app sets the Qt platform to offscreen, runs the CLI dispatcher, and returns. QML is never loaded. Otherwise it falls through to the GUI path: create the app, install the translator and theme, build the Backend, load Main.qml, start the event loop (main.cpp:40–86).

Tangible win Given any invocation, you can now say which frontend runs and why — and you can prove it by running the app with no display.

Three Qt words you need today

TermWhat it means here
QApplicationOwning object for the GUI event loop. app.exec() hands control to Qt until quit.
QQmlApplicationEngineLoads QML and creates the window tree from qrc:/Main.qml — a path into the binary's embedded resources, not the filesystem (resources.qrc).
Context propertyA C++ object injected into QML under a name. backend, theme and translator are set this way at main.cpp:65–67.

Qt can do this because Backend derives from QObject: its properties, methods and signals are visible to QML through Qt's meta-object system. That is the whole trick — see the official QML/C++ integration overview.

The seam: one facade, four inner layers

Only Backend faces QML. It exposes roughly 30 Q_INVOKABLE methods and properties, then owns four objects that know nothing about QML (backend.h:170–174):

Backend  ──► Store            (SQLite sidecar)
         ──► FileHistory      (whole-file undo/redo)
         ──► DeckRepository   (plain-text decks + watcher)
         ──► StudyPlanner     (due/new availability snapshot)
         ──► StudySession     (one sitting: queue + ratings)

This is a deliberate boundary: studyqueue.h:17–18 says the queue must stay free of DB and QML concerns. When you change scheduling, you work inside that boundary; when you change a shortcut, you work in Main.qml:285–452 and call a Backend method.

Retrieval practice

Close the reference sheet before answering. Immediate feedback is the point.

Try it in your terminal

./bin/build && ./bin/test
OMACARDS_DECKS_DIR=/tmp/omacards-lesson \
OMACARDS_STATE_DB=/tmp/omacards-lesson/state.db \
./build/omacards check --json

bin/build runs qmake6 then make (bin/build). bin/test builds the Qt Test binary and forces QT_QPA_PLATFORM=offscreen because tests need no visible window (bin/test, CI workflow). The two environment variables isolate this check from your real decks — the same mechanism the test suite uses.
